# agent-usage-skill

> 本地多 AI Agent Token 用量统一监控 Skill

监控你电脑上所有 AI Agent 的 token 用量，统一看板展示。**插件化架构**——装了新 Agent，丢一个插件文件就能接入；**实时监控**——数据源一变，看板自动刷新；**Skill 接口**——写了 SKILL.md，任何 AI 都能自动发现并调用。

## 功能

- 总用量 KPI、每日趋势堆叠柱（含区间平均日用量）、各 Agent 对比、模型 TOP15、会话明细
- 区间平均日用量：今天 / 近 3 天 / 7 天 / 14 天 / 30 天 / 90 天 / 全部，自动算对应区间日均；
  默认**近 3 天**，并记住你的上次选择（localStorage）
- 实时推送（SSE），数据源变化即自动刷新
- 单文件 exe，无需安装 Python
- 本地运行，数据不上传
- **Agent API**：结构化 JSON 返回，AI 直接调用，不用解析复杂数据

## 快速开始

1. 下载 `dist/agent-usage.exe`
2. 双击运行，自动打开 http://127.0.0.1:8765/
3. 看数

命令行参数：

```
agent-usage.exe [--port 8765] [--no-open] [--interval 5] [--full]
```

| Agent | 精确度 | 数据源 | 说明 |
| --- | --- | --- | --- |
| Codex / Claude | 精确 | CC Switch `proxy_request_logs` | 代理层记录每次请求的 input/output/cache tokens |
| Kimi Code | 精确 | `~/.kimi/sessions/**/wire.jsonl` | 本地 wire 协议含 token_usage |
| WorkBuddy | 精确 | `~/.workbuddy/projects/**/*.jsonl` | 每轮模型调用带 `usage`（prompt/completion/total_tokens），逐轮累加即真实计费量 |
| CodeBuddy | 估算 | `~/.codebuddy/projects/**/*.jsonl` | 文本长度估算 |
| 豆包工作 | 四层校准 | timeline API → Local Storage → IndexedDB 参考 → trajectory | 云端应用；系数由**消息级对齐**实测（见下节） |
| 千问工作 | 估算 | `~/.qwenworkcn/projects/**/*.jsonl` | jsonl 无 usage 字段，文本长度估算 |
| ZCode | 精确 | `~/.zcode/cli/db/db.sqlite` | 本地 SQLite 用量记录 |

> 标"估算"的 Agent 本地没有精确 token 用量，按文本长度或费用折算，仅供参考。

### WorkBuddy 口径说明（踩坑记录）

WorkBuddy 的 jsonl 每轮调用都带真实 `usage`，但有两个坑：

1. **同一行内会出现两个 usage 字典**（原始 API 返回 + 规范化版本，字段分别是
   `prompt_tokens/completion_tokens` 与 `input_tokens/output_tokens`），
   它们描述同一次调用，**只能取一个**，否则总量恰好翻倍（实测 raw/nodedup = 2.00）。
2. `prompt_tokens` 每轮携带完整历史（实测前 60 轮 57 次单调递增），
   所以**逐轮累加 `total_tokens` 就是真实计费量**，无需换算。

不要用 `session_usage.credit_json` 折算 token：那是**费用**字段（元），
与 token 的比值随模型费率浮动（实测 0.31x ~ 12.43x），且约 65% 的会话该字段为 NULL。

## 豆包工作插件详细说明

### 四层数据源降级架构

| 层级 | 数据源 | 精确度 | 触发条件 | 降级策略 |
|---|---|---|---|---|
| 1 | timeline API | 最精确 | 配置了 cookie | 失败→降级到本地 |
| 2 | Local Storage 百分比 | 精确 | 找到 usedThisPeriod 字段 | 失败→降级到文本 |
| 3 | IndexedDB 逐次 token | 参考值 | 扫到逐次调用的 input/output token | **仅供人工核对**，不参与日常计算（时间戳是落盘时刻，不可做时间窗对齐） |
| 4 | trajectory 文本估算 | 最粗 | 兜底方案 | 任何情况都能跑 |

> 系数校准走的是**消息级对齐**（见下节），既不依赖第 3 层的时间戳，
> 也不受第 4 层「只扫 agent 模式」的限制。

### 最终结论：`1% = 50 万 token`

```
TOKENS_PER_PCT = 500_000          # plugins/doubao.py
总量 = timeline 百分比 × 50 万
```

**当前实测：timeline 全时段 499.20% ⇒ 2.50 亿 token。**

这个数是**原始 token 量**（含重复的累积上下文），不是打折后的量——缓存折扣已经被
50 万 这个系数吸收掉了。验证：本地重建 Σ(每次调用的完整上下文 + 输出) =
**246,085,702**，看板 `499.20% × 50 万` = **249,600,000**，两者差 **1.6%**，
且重建口径与 WorkBuddy **完全同口径**。

**三条读法（必须一起遵守）：**

| 场景 | 能不能用 50 万 |
|---|---|
| 账户全时段总量换算 | ✅ **就是为它校准的** |
| 推算某个任务 / 某一天的实际 token | ❌ 会低估长任务 3 倍以上（见「边界一」） |
| 与其他 Agent 横向比用量 | ❌ 量纲不同，不可比（见「边界二」） |

### 证据链：50 万 是怎么定出来的

#### 0. 问题定义：云端只给百分比，没有绝对 token 字段

豆包是**云端应用**，本地没有权威 token 账本，而它的用量接口**只返回百分比**——
timeline API 每条只给 `quota_source.display_text`（如 `"0.15%"`），配额接口只给
`used_percent`，**没有任何绝对 token 字段**（本地与 API 都翻遍了，这是事实，不是没挖到）。

所以核心问题只有一个：**1% = 多少 token？**

#### 1. 方法：找一个「分子分母天然同一批事件」的测法

直觉上想用「本地真实 token ÷ 同时段百分比」，但时间窗对齐不可靠：本地 IndexedDB
里确实存着逐次调用的真实 `inputTokens/outputTokens`，但它的时间戳是**批量落盘时刻**，
不是调用时刻。用时间窗去框，窗口从 ±0 放宽到 ±60min，算出来的系数从 **256 万漂到 6 万**
（40 倍）——漂移这么大 ⇒ 分子分母根本不是同一批事件 ⇒ 此路不通。

真正的钥匙是一个此前被忽略的事实：

> **timeline 的每条记录 = 一条 user 消息**（`display_name` 就是消息原文），
> 而本地 agent 会话的 `trajectory.jsonl` 里也存着同一批 user 消息。

于是可以**按消息对齐**：同一条消息，一边是它引发的全部模型调用消耗（本地重建），
一边是它在 timeline 里记的百分比。**分子分母来自同一批消息，口径天然一致**，
不受「漏了哪类用量」影响——因为漏掉的部分在两边都不出现。

#### 2. 验证对齐是真的（不然一切白算）

| 方向 | 结果 |
|---|---|
| 正向：timeline 1590 条 → 本地 agent 消息 | **1325 条命中（83.3%）**，占 Σpct **80.0%** |
| 反向：本地 1366 条消息 → timeline | **1296 条命中（94.9%）** |
| 命中 key 数 | 1296 |

这一步顺手推翻了一个长期假设：既然 timeline 里 83.3% 的条目都能对上本地 agent 会话，
那「重建法只覆盖 agent 模式所以严重低估」就不成立——**timeline 记录的绝大部分
本来就是 agent 模式对话**，重建法给出的量级才是对的方向。

#### 3. 主证据：取「定义式」口径

```
① 命中密度 = Σtok(命中) / Σpct(命中)     ← 只覆盖命中批（占 Σpct 80.0%）
   含 system prompt : 243,325,388 / 399.535% = 60.9 万/1%
   不含             : 235,890,222 / 399.535% = 59.0 万/1%

② 账户系数 = Σtok(全量) / Σpct(全量)     ← 定义式 ⇒ 采用
   含 system prompt : 246,085,702 / 499.200% = 49.3 万/1%
   不含             : 238,457,569 / 499.200% = 47.8 万/1%
```

**为什么用 ② 不用 ①**：② 是定义式，口径与用途（把 499.2% 换算成总量）完全一致；
① 只覆盖命中的那一批，而**命中的 key 偏长任务**（长任务每 1% 代表的原始 token 是
短对话的 7.7 倍）⇒ ① 的密度天然偏高，是「命中批的密度」，不是「账户的系数」。

⇒ **采用 `TOKENS_PER_PCT = 500_000`（49.3 万取整到 10 万粒度）。**

#### 4. 交叉验证：256K 上下文窗口给出的上界

这一条**完全独立**于匹配率，只依赖一条铁律：**单次 API 调用消耗不可能超过模型上下文窗口**。

`doubao-seed-2-1-turbo` / `-pro` 的窗口 = **256K**（火山引擎官方文档）。本地实测
agent 模式单次「调用时上下文」：中位 **65,416** / p90 **189,424** / max **242,683** tok。

**max 那次是最紧的约束**：242,683 + system prompt 2,671 = **245,354**，距 262,144
窗口只剩 **16,790 tok** —— 这就是**所有本地看不见的消耗（tool schema 每次重发、
推理 token……）每次能占的全部余量**。

| 系数 | 全时段总量 | 账户均值 | 漏算/次 | max 那次真实消耗 | 判决 |
|---|---|---|---|---|---|
| 47.8 万 | 2.39 亿 | 83,550 | −2,615 | 242,739 | ✅ 窗口内（低于可见量，偏小） |
| **50 万** | **2.50 亿** | **87,395** | **1,230** | **246,584** | ✅ **现行（定义式）** |
| 55 万 | 2.75 亿 | 96,134 | 9,970 | 255,324 | ✅ 窗口内（非定义式值 ⇒ 不采用） |
| 58 万 | 2.90 亿 | 101,378 | 15,214 | 260,568 | ✅ 临界 |
| 59 万 | 2.95 亿 | 103,126 | 16,962 | 262,316 | ❌ 该次调用突破窗口 |
| 120 万 | 5.99 亿 | 209,748 | 123,583 | 368,937 | ❌ 突破窗口 41% |
| 230 万 | 11.48 亿 | 402,017 | 315,852 | 561,206 | ❌ 突破窗口 1.14 倍 |

⇒ **系数上界 58.9 万/1%**（能否定 120 万 / 230 万，但定不了真值；真值取定义式）。
50 万 落在区间内、且等于定义式值 ⇒ 采用。

> ⚠️ 上界依赖「2856 次调用 = 账户全部消耗」；若有未落盘的调用，上界相应放宽。
> ⚠️ 若将来发现 agent 会用 1M 窗口模型，此上界需放宽（当前本地无此证据）。

#### 5. 被排除的取值（证据链的一部分）

历史上出现过若干错值，根因高度一致：**重复计算**——把「一次调用」算成了两次。

| 取值 | 排除依据 |
|---|---|
| 150 万 / 120 万 / 230 万 | 让单次均值达到窗口的 71% / 80% / 153%，物理不可能 |
| 113.6 万（重建法 v2） | 在 tool 消息处多加一次「上下文重放」，模型调用数从 2856 虚增到 **5595**（= assistant 2856 + tool 2739，**这个数字就印在它自己那张表的表头里**，是当场可查的自证） |
| 500 万 | 无依据的十倍误改 |

复现（用现行数据重跑 v2 算法，`tool` 行计为一次调用）：

| 算法 | 模型调用数 | 重建总量 | 隐含系数 |
|---|---|---|---|
| v2（tool 行也算调用） | 5,899 | 4.782 亿 | **95.8 万** |
| v3（只有 assistant 行 = 一次调用） | 2,856 | 2.385 亿 | **47.8 万** |
| 膨胀倍数 | 2.07x | **2.01x** | **2.01x** |

**这个方向的错误特别危险**——它看起来"更完整、更保守"，实际是虚高。

> **教训：多算法一致 ≠ 多证据。** 曾经的「7 个算法收敛」里 6 行是同一基数的加常数
> 变体，第 7 行是把同一份错误重建拿去对齐——它们**共享同一个错前提**，
> 所以"收敛"是算术恒等式。只有当各算法的前提互相独立时，一致才有说服力。

### 三个必须知道的适用边界

#### 边界一：1% ≠ 固定 token 数（按任务长度浮动 7.7 倍）

按任务长度分型实测：

| 任务类型 | key 数 | Σpct | Σtok | 每 1% 对应的原始 token |
|---|---|---|---|---|
| 短对话（<3 次调用） | 1130 | 227.2% | 0.478 亿 | **21.1 万** |
| 中等（3~10 次） | 119 | 72.5% | 0.338 亿 | **46.7 万** |
| **长 agent（≥10 次）** | **47** | **99.9%** | **1.617 亿** | **161.9 万** |

**同一份额度，长任务每 1% 代表的原始 token 是短对话的 7.7 倍。**
而且 47 个长任务吃掉 **66% 的 token，却只占 20% 的额度**。

机制：**agent 长循环里绝大部分 input 是重复的累积上下文，云端按缓存折扣计费**，
于是 1% 在长任务里覆盖多得多的原始 token。这也解释了为什么「本地 token ↔ pct」的
双对数相关系数只有 **r = 0.185**（若严格正比应接近 1）——不是对齐错了，
而是 **% 本身就是个打折后的计费刻度，不是 token 计数**。

⇒ **50 万 是账户混合平均，不是物理常数。** 若某天以长 agent 任务为主，
真实量级可能是 `pct × 161.9 万`，是 `pct × 50 万` 的 3 倍以上。

#### 边界二：跨 agent 的 token 数不可横向比较

实测样本（2026-09-22）：

| | WorkBuddy 9/22 半日 | 豆包 9/21 全日 |
|---|---|---|
| 显示值 | 188,743,052（1.887 亿） | 32,754,999（3275 万） |
| 来源 | 逐轮累加 jsonl 的 `usage.total_tokens`，**`est=0` 精确** | 65.51% × 50 万，**`est=1` 靠百分比反算** |
| input 占比 | **99.3%** | 本地无计数 |
| output 占比 | **0.70%** | 本地无计数 |
| cache_read | 占 input **39.3%**（当日）/ 70.8%（全历史） | 不可见（已在云端折进 %） |

**根因：WorkBuddy 记的是「传输量」，豆包记的是「折后计价量」。**

- **WorkBuddy = 传输量。** input 是「每轮把整段对话重新发一遍」的累加，本质是流量。
  极端样本会话：`in=134,229,899 / out=1,103,230` = **122 : 1**——整个会话累计重发了
  1.34 亿 token 的上下文，模型只产出 110 万。该值随轮次近似**二次增长**
  （Σ 轮次 × 上下文长度），与「实际处理了多少新内容」无关。
- **豆包 = 折后计价量。** `%` 是云端打过缓存折扣的**计费刻度**，重复上下文近乎免费，
  所以同样规模的重发流量只扣很少额度；再 × 50 万换算成 token，数字天然小。

⇒ **「1.887 亿 vs 3275 万」不是 5.8 倍的使用量差，是两种量纲的差。**
本看板的正确读法：**同一 agent 内纵向可比，跨 agent 横向不可比。**
跨工具谈「谁用得多」，只有先统一到同一口径才有意义。

#### 边界三：总量可信，按天仅供参考

每日数值是 `pct` 按比例分摊的结果，**不要把它当成「那天真的过了这么多 token」**。

想按天修正，三条路**实测全部堵死**：

| 方案 | 实测结果 |
|---|---|
| 用 `trajectory.jsonl` 的 mtime 归属日期 | 跨天会话被整体挪到「最后修改日」。9/21 归属 **900 turns**，而 timeline 当天只有 **321 条** ⇒ 约 3 倍虚高 |
| 用消息文本与 timeline 对齐 | key 取 `_norm(text)[:40]` 会碰撞（「继续」「好的」等短消息跨会话合并），9/12 算出 **829 万/1%**（正常区间 10~350 万）的荒谬值 |
| 直接读消息时间戳 | `trajectory.jsonl` **只有 `role` / `content` 两个字段**，不含任何时间字段 |

⇒ **不要再尝试按天精确还原，已穷尽。**

### 已知偏差：推理（thinking）token 本地不可见

豆包 planner 用 `doubao-seed-2-1-turbo-260628`，配置里 `deep_thinking_auto: optional`，
**确实会产生推理 token**。但 `trajectory.jsonl` 只记 `user` / `assistant` / `tool`
三种 role，**没有任何 reasoning / usage 结构化字段**（已递归扫描全部字段名确认）
⇒ 推理 token 消耗了但本地看不见，重建值天然偏低。

但它**不足以改变量级**。推理只加在**输出侧**，而 agent 模式的消耗 99.6% 在输入侧：

| 消耗拆解 | 占比 |
|---|---|
| 输入侧 Σ(调用时上下文) | 238,457,569（**99.6%**） |
| 输出侧 Σ(assistant 本条) | 944,405（0.4%） |

| 推理量 = 可见输出的 R 倍 | 总消耗增幅 | 修正后系数 |
|---|---|---|
| R = 3 | +0.8% | 50.4 万 |
| R = 10 | +3.6% | 51.8 万 |
| R = 20 | +7.5% | 53.7 万 |

**要让 50 万涨到 230 万，总消耗需 +360%，即推理量须达可见输出的 914 倍——不现实。**
推理缺失是**已量化的有界偏差**，远小于「任务长度」造成的 7.7 倍差异。

**旁证（WorkBuddy 真实 usage 实测）**：全量 30,189 次调用统计——推理占**输出** 53.0%，
但因输入侧占 99.3%，推理**仅占总量的 0.35%**。豆包 agent 模式结构相同（输入侧 99.6%）。

### 建模陷阱（改算法前必读）

**正确模型**：一次 assistant 消息 = 一次模型调用，消耗 = `累积上下文 + 本条输出`。

1. **漏算**：只算消息体，忽略上下文重发 → 得 47.8 万。
2. **重复算（更隐蔽）**：不可在 tool 消息处额外加一次「上下文重放」——工具结果已经
   进了 `ctx`，下次调用的 `ctx_before` 本就包含它 ⇒ 同一份 input 算两遍，高估约 2 倍。
3. **连续 user 消息必须合并成一个工作单元**：用户会连发短消息（「你看看」→「还是这个啊」），
   模型只回一次，而 timeline 给每条都记了 pct。若把整轮消耗全算给最后一条，
   前面的 key 拿到 pct 却 token = 0 ⇒ **系数被系统性拽低 2~4 倍**。应在单元内均摊。
4. **user 消息本身也是 input**，必须计入累积上下文。
5. **别用时间窗对齐真实 token**：要验证对齐真假，用**消息文本匹配率**，不要用时间窗。
6. **别假设「没扫到的就是没算的」**：先测匹配率再下结论。

### 一键复现

```bash
python tools/calibrate_doubao.py                 # 只算不改：打印双向匹配率 + 两个口径 + 推荐值
python tools/calibrate_doubao.py --apply         # 写回 plugins/doubao.py
python tools/calibrate_doubao.py --anchor 1.5e8  # 有绝对配额时一击钉死
python tools/calibrate_doubao.py --root "D:/xx/DoubaoWork/User Data/Default"   # 换机器
```

```bash
python tools/calibrate_doubao.py --anchor <一个7天窗口的token数> --apply
```

- 用户已确认：百分比是**累加**的（首窗 + 重置 4 次 = 500%），不是单窗口封顶。

### 可选 cookie 配置

如果用户知道怎么从 DevTools 复制 cookie，就存到配置文件里，拿到精确的 API 数据。不知道也没关系，自动降级到本地估算。

配置文件路径：`~/.doubao-usage/config.json`
```json
{"doubao_cookie": "sessionid=xxx; passport_csrf_token=xxx; ..."}
```

> 即使配了 cookie，API 也只返回**百分比**（如 `0.15%`），绝对 token 仍需 × 50 万 换算。

## Agent API（给 AI 调用）

所有接口返回结构化 JSON，AI 直接调用，不用解析复杂数据。

### 接口列表

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 健康检查 |
| GET | `/api/plugins` | 已接入的插件列表 |
| GET | `/api/data` | 完整聚合数据 |
| GET | `/api/refresh` | 触发一次增量扫描 |
| GET | `/api/stream` | SSE 实时推送 |
| **GET** | **`/api/agent/summary`** | **精简用量摘要（推荐）** |
| **GET** | **`/api/agent/agents/<key>/usage`** | **单个 agent 详细用量** |
| **GET** | **`/api/agent/config`** | **查看本地配置** |
| POST | `/api/agents` | 添加新 agent |
| DELETE | `/api/agents/<key>` | 删除 agent |

### 示例

```bash
# 拿摘要（AI 最常用）
curl http://127.0.0.1:8765/api/agent/summary

# 拿单个 agent 详情
curl http://127.0.0.1:8765/api/agent/agents/doubao/usage

# 检查豆包 cookie 是否已配置
curl http://127.0.0.1:8765/api/agent/config

# 触发扫描
curl http://127.0.0.1:8765/api/refresh
```

## 接入新 Agent

### 方式一：插件文件

在 `plugins/` 新建 `<name>.py`：

```python
KEY = 'myagent'
NAME = '我的 Agent'
ESTIMATE = False
WATCH_PATHS = ['%USERPROFILE%\\.myagent\\data']

def scan(full, need, mark):
    return [...]
```

重启即可。

> **插件返回 `daily` 时的硬性约定**：`daily` 表主键是 `(agent, day, source_file)`。
> 若你的插件在 `daily` 里用**同一个 `source_file`** 上报多条同一天的数据，它们会互相覆盖，
> 导致「总用量正确、但按天曲线偏低」。凡是**一个数据源内含多个会话**（如读一张 DB 表、
> 一个目录下的多个会话）的插件，`source_file` 必须**按会话唯一**（例如 `f'{DBP}#{session_id}'`）。
> 会话天然分散在不同文件的插件（多数 jsonl 类）不受影响。

### 方式二：API 自助接入

```bash
curl -X POST http://127.0.0.1:8765/api/agents \
  -H "Content-Type: application/json" \
  -d '{"name": "MyAgent", "data_path": "C:/Users/you/.myagent/sessions/a.jsonl"}'
```

找不到数据时会返回结构化提示，告诉你去哪找。

## 兜底方案

任何一个数据源失败，都自动降级到下一层，不会崩：

| 场景 | 兜底行为 |
|---|---|
| API 超时/401 | 降级到 Local Storage 百分比 |
| Local Storage 没数据 | 降级到 trajectory 文本估算 |
| IndexedDB 被锁 | 跳过，不影响其他数据源 |
| 某个插件崩了 | 其他插件正常扫描 |
| 服务挂了 | 数据还在 JSON 文件里，重启自动加载 |
