# 豆包 token 系数校准（已固化，勿重推）

仓库：本仓库根目录（GitHub Zaosusu/agent-usage-skill）
系数推导全文：[`docs/DOUBAO.md`](DOUBAO.md)（「豆包 1% = 50 万 token 是怎么来的」）

> **换算直接用 `总量 = timeline 百分比 × 500_000`，别再重推。** 本文是操作与排障手册。

## 一、先用结论，别再推导

| 项 | 值 | 状态 |
|---|---|---|

**关键认知（2026-09-22 复核后确立）**：
1. 此前认为「重建法只覆盖 agent 模式所以严重低估」——**这个假设是错的**。
   实测 timeline 里 **83.3%** 的条目都能对上本地 agent 会话的 user 消息。
2. **六个错值里有五个偏高，根因都是「重复计算」**（把一次调用算成两次）。
   最典型：113.6 万 在 tool 消息处多加一次上下文重放 ⇒ 模型调用数 2856→5595（1.96 倍）。
   这种错误特别危险，因为看起来"更完整、更保守"，实际是虚高。

**当前换算结果**：timeline 全时段 **499.20%** ⇒ **2.50 亿 token**（13 天）。
单独取豆包（`monitor.py summary` 里 `estimate=1` 那条）显示 `249,599,994`。

> ⚠️ **拿不到就报错，不会给错数**（2026-09-22 起）：该值**只在 timeline API 成立**。
> 早前有一个 cookie 失效降级分支读 Local Storage 的 `local-quota`，那里乘系数是错的，
> 会静默掉到 **141.5 万**（低估 176 倍）—— 该分支连同降级逻辑已**删除**。
> 现在 cookie 失效会直接 `status=error` 并提示补 cookie（旧数据保留），
> 所以**看板豆包数不再会暴跌**；若真跌了，先看 `monitor.py scan` 的 error 行。

## 一·补、判决性检验：上下文窗口（只给上界，能否定大错值）

**任何系数的账户平均单次调用消耗，都不可能超过模型上下文窗口。**

**第一步：先确定窗口到底多大**（早前用 128K 是错的，已更正）：
`doubao-seed-2-1-turbo` / `-pro` 均为 **256K**（火山引擎官方套餐文档），
本地配置里出现过的模型也只有这两个 256K 系列 + `doubao-seed-character`
（角色扮演，窗口更小），**没有任何 1M 窗口模型**。
⇒ agent 模式每次调用都在 **256K** 内。

> ⚠️ 我此前按 **128K** 判决，是错的：实测单次上下文 p90 = 189,424、
> **max = 242,683**，两者都超 128K —— 若窗口真是 128K，这些调用不可能存在。

**第二步：用 max 那次调用反推上界**（这是全篇最紧的一条约束）：

```
实测 max 单次可见上下文      = 242,683
+ system prompt（每次重发）  =   2,671
                          ─────────────
                            245,354   距 256K 窗口只剩 16,790 tok
```

这 **16,790 tok 就是全部「看不见的消耗」每次能占的总预算**
（tool schema + 推理 token + 图片 + 非 agent 摊薄）。

⇒ **系数上界 = (可见单次 86,164 + 16,790) / k = 589,019 ≈ 58.9 万/1%**

| 系数 | 账户均值 | 漏算/次 | max 那次的真实消耗 | 判决 |
|---|---|---|---|---|
| 47.8 万 | 83,550 | −2,615 | 242,739 | ✅ 窗口内（低于可见量，偏小） |
| **50 万** | **87,395** | 1,230 | 246,584 | ✅ **现行（定义式取整）** |
| 55 万 | 96,134 | 9,970 | 255,324 | ✅ 窗口内（非定义式值 ⇒ 不采用） |
| 58 万 | 101,378 | 15,214 | 260,568 | ✅ 临界 |
| 58.9 万 | 103,000 | 16,790 | 262,144 | ⚠️ 恰好触顶（上界） |
| 120 万 | 209,748 | 123,583 | 368,937 | ❌ 该次调用突破窗口 |
| 230 万 | 402,017 | 315,852 | 561,206 | ❌ 超窗 1.14 倍 |

**这条检验只能给「上界」，定不了真值**：
- **上界 58.9 万** = max 调用占满窗口后，留给全部漏算项（schema/推理/图片/非agent）的预算
- **下界** = 可见消耗的实测密度（定义式 Σtok/Σpct，见「二」）
⇒ 50 万 落在区间内，且等于定义式值 ⇒ **采用 50 万**。
⚠️ 上界依赖「2856 次调用 = 账户全部消耗」；若有未落盘的调用，上界相应放宽。
⚠️ **更关键的边界见「二·补」：1% ≠ 固定 token 数。**

脚本已内置该检验（输出第 ③ 段），跑一次即可看到全部历史系数的判决。
⚠️ 若将来发现 agent 会用 1M 窗口模型，此上界需放宽（当前本地无此证据）。

**注意别误用**：这个检验只适用于「每行是单条增量消息」的数据。
豆包 `trajectory.jsonl` 确认是**单条增量**（role 明确交替、长度几百~几千、不随行号增长），
所以累积式重建正确。

⚠️ **不要用 WorkBuddy 当尺子量豆包**（2026-09-22 踩过并已查清）：
WorkBuddy 的 jsonl **带真实 usage**（`total_tokens` 等），根本不需要估算；
它的行结构是 `message`/`function_call`/`function_call_result`/`reasoning` 等
**事件流**（`含 messages 数组的行 = 0`，即**不是快照**）。
此前我曾对它套用「累积式重建」并算出「真实/估算 ≈ 0.52」，
那是**算法用错了**（该数据有真实 usage，不该估），不是估算偏差，**该结论已废弃**。

## 一·补2、推理（thinking）token 不可见 —— 影响有界，别被它带偏

**事实**：豆包 planner 用 `doubao-seed-2-1-turbo-260628`，配置含
`deep_thinking_auto: optional` / `enable_launcher_deep_think: true` / `systemReasoningModel`，
**确实产生推理 token**；但 `trajectory.jsonl` 只记 `user`/`assistant`/`tool`
三种 role，**递归扫描全部字段名后确认无任何 reasoning/usage 结构化字段**
⇒ 推理消耗了但本地看不见，重建值天然偏低。用户对此的质疑完全正确。

**但它撑不起大系数**，因为推理只加在**输出侧**，而 agent 模式消耗 99.6% 在输入侧：

| 消耗拆解 | 占比 |
|---|---|
| 输入侧 Σ(调用时上下文) | 99.6% |
| 输出侧 Σ(assistant 本条) | 0.4% |

| 推理量 = 可见输出的 R 倍 | 系数变化 |
|---|---|
| R = 3 | 50 → 50.4 万 |
| R = 10 | 50 → 51.8 万 |
| R = 20 | 50 → 53.8 万 |

**要到 230 万需推理量达可见输出的 ~900 倍 —— 不现实。** R=20 时系数也只到 53.8 万。

**旁证（WorkBuddy 真实 usage 实测，30,189 次调用）**：WorkBuddy jsonl 带真实
`completion_tokens_details.reasoning_tokens`，统计得：
- 推理占**输出** = **53.0%**（推理确实很多）
- 推理占**总量** = **仅 0.35%**
- 输入侧占比 = **99.3%**

⇒ 推理占输出一半，但对总量只贡献 0.35%。豆包结构相同，故推理缺失影响可忽略。

## 一·补3、WorkBuddy 不需要修（已核实，2026-09-22）

用户问「那 WorkBuddy 也要修复？」——**不需要**。核实结论：

- WorkBuddy 用的是**真实 `usage.total_tokens`**（不是估算），且按
  `providerData.messageId/requestId` 去重（重复 key 仅 14 个 / 30,206 条）。
- 去重后 Σtotal = **38.13 亿**，看板显示 **37.77 亿**，差异 **0.93%**
  （增量扫描的时间差，正常）。
- 含 usage 的行只有 `function_call`(26,883) 与 `message`(3,323) 两类，
  `file-history-snapshot`/`reasoning` 等行**不带 usage**，不会混入重复计数。
- ⇒ **WorkBuddy 数据准确，无需修复。** 需要系数校准的只有豆包（云端只给百分比）。

## 二、★ 现行方法：消息级对齐（直接测量）

**钥匙**：timeline 每条记录 = 一条 user 消息（`display_name` 就是消息原文），
本地 `trajectory.jsonl` 里也存着同一批 user 消息 ⇒ 可以**按消息对齐**。
分子分母来自同一批消息，口径天然一致，不受「漏了哪类用量」影响。

**第一步：先验证对齐是真的**（匹配率低则结论作废）

| 方向 | 结果 |
|---|---|
| 正向 timeline → 本地 | 1325/1590 条 = **83.3%**，占 Σpct 80.0% |
| 反向 本地 → timeline | 1296/1366 条 = **94.9%** |
| 双对数相关系数 r | **0.185** ⇒ % 与原始 token **非严格正比**（见「二·补」） |

**第二步：两个口径夹出区间**

```
① agent 内容密度 = Σtok(命中) / Σpct(命中)
   含 system prompt : 243,325,388 / 399.535% = 60.9 万/1%
② 账户系数 = Σtok(全量) / Σpct(全量)   ← **采用这个**（定义式：raw 总量 ÷ 百分比总量）
   含 system prompt : 246,085,702 / 499.200% = 49.3 万/1%
⇒ 取整 = 50 万。
⚠️ ①（命中密度）偏高：命中的 key 偏长任务，其密度天然高于账户混合平均（见「二·补」）。
```

```bash
python tools/calibrate_doubao.py            # 打印双向匹配率 + 两口径 + 推荐值
python tools/calibrate_doubao.py --apply    # 写回 plugins/doubao.py
```

## 二·补、2026-09-22 修掉的两个真 bug（会显著改变结果）

1. **连续 user 消息必须合并成一个「工作单元」**。用户会连发短消息
   （「你看看」→「还是这个啊」），模型只回一次，而 timeline 给每条都记 pct。
   旧实现把整轮消耗全算给最后一条 ⇒ 前面的 key 有 pct 无 token ⇒ **系数被拽低 2~4 倍**。
   实测 1504 条 user 消息里有 **887 处连续相邻** —— 量级不小，必须合并。
   现在单元内均摊：Σ(单元内各 key) = 单元总消耗。
2. **user 消息本身也是 input**，必须计入累积上下文（旧实现漏了）。

修完后：正向匹配 83.3%（原先 90.0%，去掉虚高）、反向 94.9%（原先 95.2%），
账户系数 49.3 万（原先 48.2 万），推荐值仍是 **50 万**。

## 三、钉死精确值的唯一办法

豆包 **timeline API 只返回百分比**（`quota_source.display_text` = "0.15%"），
配额接口只返回 `used_percent`，**本地与 API 都没有绝对 token 字段** —— 这是事实，不是没挖到。

所以真正能一击钉死的锚点 = **「一个 7 天窗口（100%）= 多少 token」**。
来源：豆包用量页「占 7 天额度」旁的绝对已用/总额，或订阅计划的单窗口配额。

```bash
python tools/calibrate_doubao.py --anchor <该数字> --apply
```

用户已确认：百分比是**累加**的（首窗 + 重置 4 次 = 500%），不是单窗口封顶。

## 四、改完系数必做（否则白改）

1. **停 serve**：后台 watcher 每 5 秒会用旧代码把数据写回。
   ```bash
   netstat -ano | grep ":8765"      # 找 LISTENING 那行的 PID
   MSYS_NO_PATHCONV=1 taskkill /F /PID <pid>
   ```
2. 重扫：`python monitor.py scan --agents doubao --full`
3. 重启（**必须后台 + 输出重定向，见下方铁律**）：
   ```bash
   python serve.py --port 8765 > "%TEMP%/serve_8765.log" 2>&1
   ```

### ⚠️ 启 serve 的铁律：绝不要接 `| head`

```bash
python serve.py --port 8765 | head -5     # ❌ 死法
```

管道读满 5 行就关闭 ⇒ 服务进程被 SIGPIPE 干掉或**卡死**。
症状非常具有迷惑性：**端口仍在 LISTENING，但 curl 返回 HTTP 000 / exit 52**——
看着像活着，实际完全不响应。排查时会误判为"看板没数据"，浪费大量时间。

正确姿势：后台启动 + 输出重定向到日志文件（见上）。

**探活**（启动后必做，别只看 netstat）：
```bash
curl -s -o /dev/null -w "HTTP %{http_code}" --max-time 8 "http://127.0.0.1:8765/"
```
必须拿到 `HTTP 200`；不是 200 就 `taskkill` 重来。

**看板提示「ECharts 加载失败（需联网 CDN）」**：离线兜底提示，联网刷新即可，不是 bug。

## 四·补、本地存档：高水位 + 完整时序（2026-09-23）

豆包云端只给**累计百分比**，且用量页只展示**最近半年** ⇒ 旧条目会掉出、累计值可能回落。
为此在引擎的 `data/usage.db` 里存两份存档（**已不再是独立 JSON 文件**）：

| 表 | 内容 |
|---|---|
| `agent_high_water` | 累计量高水位（每 agent 一行） |
| `agent_usage_history` | 每 agent 每天的 `pct` / `tokens` 完整时序 |

- **只增不减**：总量取 `max(历史高水位, 本次接口值, 逐日并集之和)`；按天写入取 `max(旧值,新值)`。
- **容差 0.5%**：低于高水位 0.5% 内视为抖动放行，超过则触发保护并在 `source_file` 标注原因。
- **曲线不丢**：每次扫描把「本地时序 ∪ 本次接口按天」取大后回灌，接口只回半年也不影响历史曲线。
- **迁移**：早期存 `data/doubao_history.json` 的孤儿文件会在首次运行自动迁入 DB 并删除。

查存档：

```sql
select * from agent_high_water;
select day,pct,tokens from agent_usage_history where agent='doubao' order by day;
```

## 五、排障套路

| 症状 | 第一动作 |
|---|---|
| **看板打不开 / 无响应** | 先查是不是启 serve 时接了 `| head`（见四之铁律）；再 `curl` 探活要 200 |
| **豆包用量取不到 / scan 报错** | **先看报错文案区分类型**（见下方「网络抖动 ≠ cookie 过期」），别一看到报错就去重新登录补 cookie |
| **总量对、按天曲线为空** | 跑下方 SQL 定位缺哪个 agent，**别去怀疑系数** |
| 豆包数字明显偏离直觉 | 跑 `tools/calibrate_doubao.py`，看双向匹配率与两口径 |

### ⚠️ 网络抖动 ≠ cookie 过期（2026-09-23 踩过）

SSL 层实测存在**偶发抖动**（`UNEXPECTED_EOF_WHILE_READING`），表现为 `scan` 报
「豆包用量取不到」。**这不是 cookie 过期**。判定方法：`curl https://www.doubao.com/`
能通（哪怕 302）+ DNS 正常 ⇒ 就是网络抖动，稍后重扫即可。

已做两处加固：
1. `_request_page()` 带**指数退避重试 3 次**（0.8s/1.6s）—— 整轮要翻 80+ 页、
   耗时 2 分钟，单页抖动不该让整轮白费。4xx 是确定性错误，不重试直接上抛。
2. 报错文案**按类型分流**：`_last_error` 记 `('net',…)` / `('auth',…)`，
   网络类明确写「与 cookie 无关，cookie 仍是好的，无需重新登录」。

### ⚠️ `scan done at` 曾是「开始时刻」（2026-09-23 修）

`generated_at_str` 在扫描**开头**生成，长扫描下与完成时刻差几分钟，
却打印成 `scan done at`，排障时容易把开始时刻误读成完成时刻。
现改为分两行：`scan started at … (耗时 Xs)` + `scan finished at …`。

**「总量对、按天曲线为空」**——先跑这一句定位，别去怀疑系数：

```sql
SELECT agent, COUNT(*), SUM(tokens) FROM daily GROUP BY agent;
```

缺哪个 agent 一眼看出。根因通常是插件没按引擎新协议返回：
引擎要 `scan()` 返回 `{'sessions', 'daily', 'daily_files'}`，只 `return sessions`
会导致 daily 表一行不写（豆包 2026-09-21 踩过，已修 `_wrap_result()`）。
另外 daily 主键是 `(agent, day, source_file)`，`source_file` 必须按天唯一（如 `doubao-2026-09-21`），
否则同一天互相覆盖。

## 六、已排除的错误路径（别重走）

- **IndexedDB 时间窗硬锚点 —— 已证伪，别再当锚点用**。
  该库确实存着真实逐次调用的 `inputTokens/outputTokens`，但：
  ① 窗口从 ±0 放宽到 ±60min，系数从 **256 万漂到 6 万（40 倍）** ⇒ 分子分母不是同一批事件；
  ② 该库全量字节里 `quota_source_code` 出现 **0 次**，「同额度池」无法证明（此前是编造的）；
  ③ 那 65 条记录时间集中在 01:46~01:59，是 memory 压缩**批量落盘**时刻，非调用时刻；
  ④ 内容是陪伴/角色扮演会话（`storyMode`/`mood`/`sceneConstraints`），与 agent 循环不同。
  结论：该数据**只能做人工核对参考**，不可做时间窗对齐。
- **WorkBuddy 不能当校准尺**：它的 jsonl 每条记录含大量内容，按同样方法累积会膨胀到 838 亿
  （真实仅 37 亿，R=0.04），与豆包的 trajectory 结构不可比，比值不可用。
- **Local Storage 配额是另一体系，且曾是真 bug（2026-09-22 实测 → 已修）**：
  该池 `usedThisPeriod/monthlyLimit` = **566/20000 = 2.83%**，同期 timeline 是 **499.20%**，
  **差 176 倍**；字段是 `type:model` / `plan:premium` / `billingMode:metered`，
  周期 2026-07-09→10-31（**与 7 天窗口无关**），单位疑似按次或点数而非 token。

- **其他本地途径全部实测排除**（2026-09-22）：`netmain-*.alaudalog`（每日 40~60MB）

## 七、建模陷阱（改算法前必读）

**正确模型**：一次 assistant 消息 = 一次模型调用，消耗 = `累积上下文 + 本条输出`。
system prompt 每次调用都要重发，作为独立分量叠加。

**三个已踩的坑**：
1. 漏算（早期）→ 只算消息体，得 47.8 万。
2. **重复算**（更要命）→ 在 tool 消息处额外加一次「上下文重放」，
   但工具结果已进 ctx，下次调用的 `ctx_before` 本就包含它 ⇒ 同一份 input 算两遍，
   高估约 2 倍，得出「113.6 万」。脚本里已写明，**不可再加**。
3. **用时间窗对齐真实 token** → IndexedDB 时间戳是落盘时刻，系数随窗口宽度剧烈漂移。
   验证对齐真假要用**消息文本匹配率**，不要用时间窗。

**别假设「没扫到的就是没算的」**：先测匹配率再下结论。这里正向 83.3%、反向 94.9%
说明两边高度重合，而非「只覆盖一小部分」。

tool schema 本地不落盘（trajectory 只存 tool_calls 不存 schema）。

⚠️ **此处我犯过一次推理错误，务必记住**：我曾写「现行消息级对齐法不再依赖 schema 假设，
因为分子分母同批，schema 消耗在两边都不单独出现」——**这是错的**。
「分子分母同批」保证的只是**消息集合一致**（哪几条 user 消息），
**不是消耗量口径一致**：

| 消耗项 | 进分子（本地重建）| 进分母（云端百分比）|
|---|---|---|
| 消息文本 | ✅ | ✅ |
| system prompt | ✅（按会话均值叠加）| ✅ |
| **tool schema**（每次调用重发）| ❌ 本地不存 | ✅ |
| **推理 token** | ❌ 无 reasoning 字段 | ✅ |
| 非 agent 用量 | ❌ 没扫 | ✅ |

⇒ 凡是只进分母不进分子的项，都会让算出的系数**系统性偏低**。

这些口径差会让系数略偏低，但**影响有界**（上界 58.9 万，见「一·补」），
量级上远不如下面这条重要。

### ★ 真正的边界：1% ≠ 固定 token 数（2026-09-22 定，最重要的一条）

用户原话：「一天用 50% 额度，结果你跟我说 1% 才 50 万，50% 才 2500 万。太反直觉了」
—— **这个质疑命中了真问题**。之前把 50 万 当成「1% = 50 万 token 的活」用，是错的。
按任务长度分型实测（`calibrate_doubao.py` 输出 ①·补）：

| 任务类型 | key 数 | Σpct | Σtok | 每 1% 对应原始 token |
|---|---|---|---|---|
| 短对话（<3 次调用） | 1130 | 227.2% | 0.478 亿 | **21.1 万** |
| 中等（3~10 次） | 119 | 72.5% | 0.338 亿 | **46.7 万** |
| **长 agent（≥10 次）** | **47** | **99.9%** | **1.617 亿** | **161.9 万** |

**同样 1%，长任务对应的原始 token 是短对话的 7.7 倍。**
47 个长任务吃掉 **66% 的 token，却只占 20% 的额度**。

**机制**：agent 长循环里绝大部分 input 是**重复的累积上下文**，云端按**缓存折扣**计费
⇒ 同样 1% 在长任务里覆盖多得多的原始 token。这正是相关系数只有 r = 0.185 的原因：
**% 是打折后的计费刻度，不是 token 计数。**

**推论（怎么读数字）**：
- 「全时段 499.2% ⇒ 3.0 亿 token」✅ 对（50 万 就是为**总量**校准的）。
- 「某个 70% 的重度日 = 3500 万」❌ **错**。若那天以长 agent 任务为主，
  真实量级是 **70 × 161.9 万 ≈ 1.1 亿原始 token**，差 3 倍 —— **用户的直觉就在这里**。
- 「一堆短对话涨了 30%」也别按 50 万×30 去理解，那可能只值 21 万/1%。

**一句话：50 万 是账户混合平均，不是物理常数。谈单个任务/单天的量必须看任务长度。**

### ★ 跨工具口径不可比：WorkBuddy 的 1.87 亿 ≠ 豆包的 1.87 亿（2026-09-22 定）

用户原话：「WorkBuddy 随便用用，已经显示用量 1.87 亿了。然而豆包我昨天干了一整天，
从早干到晚，把额度用到 100%，才显示 3200 多万，真的很不合理。」
**结论：两个数字都对，但量纲不同，既不能相减也不能相比。**

实测（`agent-usage-skill` 的 `data/usage.json` / `data/usage.db`，2026-09-22 11:09 快照）：

| | WorkBuddy 9/22 半日 | 豆包 9/21 全日 |
|---|---|---|
| 显示值 | 188,743,052（1.887 亿）| 32,754,999（3275 万）= **65.51% × 50 万** |
| 口径 | 逐轮累加 `usage.total_tokens`，**est=0 精确** | 百分比反算，**est=1 估算** |
| input 占比 | **99.3%** | 本地无计数 |
| output 占比 | **0.70%** | 本地无计数 |

- **WorkBuddy 记传输量**：input 是「每轮把整段对话重新发一遍」的累加。
  极端样本 `agent-usage-skill` 会话 `in=134,229,899 / out=1,103,230` = **122 : 1**；
  该值随轮次近似**二次增长**。全历史 cache_read 27.43 亿 ÷ input 38.75 亿 = **70.8%**。
- **豆包记折后计价量**：重复上下文近乎免费，所以 % 涨得慢，× 50 万后数字天然小。
- ⇒ **不是 5.8 倍的使用量差，是两种量纲的差。**

**回答用户「哪个 AI 用最多」时必须带这句**：跨 agent 的 token 数**只能在同口径内纵向比较**，
横向直接比会得出误导结论（会让人以为豆包"用得少"，实际只是记账方式不同）。

**未决疑点（唯一可能真错处）**：用户称昨天「把额度用到 100%」，
但 timeline 实测 9/21 只有 **65.51%**。三种可能未定：
① 用户看的「100%」是豆包 App 里**另一个额度池**（如每日额度），而看板采的是 7 天周期额度
⇒ 分母不同；② timeline 漏采（部分用量未进接口）；③ 系数偏低（但 50 万 = 定义式
Σtok 246,085,702 ÷ Σpct 499.200% = 49.3 万取整，理论上不该偏）。
→ 要判定必须拿到「占 7 天额度」旁的**绝对数字**作锚点（见第三节，仍是那个遗留缺口）。

> 用户随后确认：9/21 用掉 65.51%，累计到 100% —— **数据本身是对的，疑点①②排除。**

### ★ 接上条：豆包「总量」是真实口径，但「按天」还原不了（2026-09-22 深挖）

用户进一步要求：「我要记录的是 token 用量，而不是打过折的量。」

**① 总量没有被打折。** 本地重建 `call_cost_sys` = **246,085,702**
（= Σ 每次调用的完整上下文 + 输出，**与 WorkBuddy 完全同口径**），
看板 `pct × 50 万` = 2.50 亿，**差 1.6%**。
⇒ 看板上的豆包数字**本来就是原始 token 量**；`50 万` 的物理含义就是
「折后 1% → 原始 token」的换算率，折扣在标定时已被吸收。

**② 但按天会失真**：折扣率随任务长度变（21.1 万 ~ 161.9 万/1%，差 7.7 倍），
看板用统一 50 万 ⇒ 长任务日低估、短对话日高估。想按天修正，三条路实测全堵死：

| 方案 | 实测结果 |
|---|---|
| `trajectory.jsonl` 的 mtime 当日期 | 跨天会话整体挪到「最后修改日」：9/21 归属 900 turns，而 timeline 当天只有 **321 条** ⇒ 约 3 倍虚高 |
| 消息文本与 timeline 对齐 | key 取 `_norm(text)[:40]` 会碰撞（「继续」「好的」跨会话合并），9/12 算出 **829 万/1%**（正常区间 10~350 万）的荒谬值 |
| 直接读消息时间戳 | trajectory **只有 `role` / `content` 两字段**，无任何时间字段 |

⇒ **豆包看板「总量可信、按天的 token 仅供参考」。**

⚠️ **2026-09-23 更正一处旧表述**：这里曾写「每日值是 `pct` **按比例分摊**的结果」——
**不准确**。每日 pct 其实是按接口逐条 `occurred_at_ms` **真实归属**的，
Σ每日 pct = 总 pct（实测误差 **0.0**）。所以：

- 每日的 **pct** ⇒ ✅ **精确可信**
- 每日的 **tokens**（= pct × 50 万）⇒ ⚠️ 仅供参考，因为 1% 对应的 token 数
  随任务长度浮动 7.7 倍，而每天都用同一个 50 万

即「拆分精确、换算不精确」。**不要再尝试按天精确还原 token，已穷尽。**
